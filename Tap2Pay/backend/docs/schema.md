# OrchestratePay — Database Schema

PostgreSQL 15. All tables use UUID primary keys and `TIMESTAMPTZ` timestamps.
Run `npm run migrate` to create all tables from scratch.

---

## Entity Relationships

```
merchants ──┐
            │ 1:N
            ├──── transactions ◄──── nfc_tags ◄──── consumers
            │                                           │
            └──── (via transactions.consumer_id) ───────┘

server_audit_log   (append-only, references entity_id by string)
```

---

## Tables

### `merchants`
One row per merchant terminal. Each merchant has one Sunmi P2 Pro device.

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | Auto-generated |
| `name` | TEXT | Business name |
| `phone` | TEXT | Merchant contact phone |
| `email` | TEXT UNIQUE | Login credential |
| `password_hash` | TEXT | bcrypt (cost 12) — never stored plain |
| `mpesa_shortcode` | TEXT | Paybill or till number for settlement |
| `mpesa_account_ref` | TEXT | Account reference for settlement |
| `active` | BOOLEAN | `false` = suspended, blocked from login |
| `device_id` | TEXT | Android device ID — single-device enforcement |
| `created_at` | TIMESTAMPTZ | |
| `updated_at` | TIMESTAMPTZ | Auto-updated by trigger |

**Indexes:** `idx_merchants_email` on `email`

**Design note:** `device_id` is updated on every successful login. A login from a new device overwrites the previous `device_id`, invalidating the prior JWT on next request. This enforces the one-terminal-per-account policy.

---

### `consumers`
People who tap OrchestratePay stickers. Identity is their M-Pesa phone number.

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | |
| `phone` | TEXT UNIQUE | 254XXXXXXXXX format — sent to Daraja for STK Push |
| `phone_hash` | TEXT | SHA-256 of phone — for lookups without exposing PII |
| `display_name` | TEXT nullable | Optional nickname |
| `active` | BOOLEAN | `false` = blocked from payments |
| `created_at` | TIMESTAMPTZ | |

**Indexes:** `idx_consumers_phone_hash` on `phone_hash`

**Design note:** Phone number is stored plain because it must be sent verbatim to M-Pesa. The `phone_hash` allows lookups in admin queries without revealing phone numbers in logs. In a future PCI-scoped deployment, encrypt the `phone` column with AES and only decrypt immediately before sending to Daraja.

---

### `nfc_tags`
Maps a physical NTAG215 sticker to a consumer account. Written at onboarding, locked read-only immediately after.

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | |
| `tag_id` | TEXT UNIQUE | OrchestratePay-assigned UUID written into NDEF — the primary identifier |
| `uid` | TEXT nullable | Raw 7-byte NFC hardware UID (hex) — audit log only, never used for routing |
| `consumer_id` | UUID FK → consumers | Who owns this tag |
| `active` | BOOLEAN | `false` = stolen/lost tag, will be rejected at payment time |
| `issued_at` | TIMESTAMPTZ | When the tag was programmed |
| `last_used` | TIMESTAMPTZ nullable | Updated on every successful tap |

**Indexes:** `idx_nfc_tags_tag_id` on `tag_id`

**Design note:** We use a OrchestratePay-assigned `tag_id` (not the raw hardware `uid`) as the primary identifier because:
1. The hardware UID can be cloned on cheap NFC writers
2. The `tag_id` is a UUID generated by our system and locked onto the tag at issue time
3. The `uid` is logged for fraud investigation but never used for routing

### `transactions`
The financial ledger. Source of truth for all payment state.

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | |
| `merchant_id` | UUID FK → merchants | |
| `consumer_id` | UUID FK → consumers | |
| `amount_cents` | BIGINT | Amount in KES cents (KES 50.00 = 5000) |
| `currency` | TEXT | Always `KES` for now |
| `status` | TEXT CHECK | `PENDING` → `CONFIRMED` / `DECLINED` / `FAILED` / `EXPIRED` |
| `source` | TEXT CHECK | `NFC_TAG` / `QR_CODE` / `ISO_CARD` |
| `nfc_uid` | TEXT nullable | Raw tag UID at time of tap (audit only) |
| `idempotency_key` | TEXT UNIQUE | SHA-256 key — prevents duplicate STK Pushes |
| `checkout_request_id` | TEXT nullable | Safaricom's STK Push reference — used to match callbacks |
| `merchant_request_id` | TEXT nullable | Safaricom's merchant request ID |
| `mpesa_receipt` | TEXT nullable | M-Pesa confirmation code (e.g. `NLJ7RT61SV`) — only on CONFIRMED |
| `mpesa_result_code` | INTEGER nullable | Raw Safaricom result code |
| `mpesa_result_desc` | TEXT nullable | Raw Safaricom result description |
| `created_at` | TIMESTAMPTZ | When the tap occurred |
| `confirmed_at` | TIMESTAMPTZ nullable | When the M-Pesa callback confirmed payment |
| `updated_at` | TIMESTAMPTZ | Auto-updated by trigger |

**Indexes:**
- `UNIQUE idx_transactions_idempotency` on `idempotency_key` — DB-level duplicate prevention
- `idx_transactions_checkout_request` on `checkout_request_id WHERE checkout_request_id IS NOT NULL` — fast callback matching
- `idx_transactions_pending` on `created_at WHERE status = 'PENDING'` — fast reconciliation queries

**State machine:**
```
                     M-Pesa callback ResultCode=0
PENDING ─────────────────────────────────────────► CONFIRMED
   │
   ├── M-Pesa callback ResultCode≠0 ──────────────► DECLINED
   │
   ├── STK Push itself failed ──────────────────────► FAILED
   │
   └── Reconciliation job after 90 min ─────────────► EXPIRED
```

**Why write PENDING before calling M-Pesa:**
If M-Pesa succeeds but our subsequent DB write fails, the consumer is charged with no record in our system. Writing PENDING first means we can always reconcile — worst case the transaction is eventually found by the reconciliation job.

### `server_audit_log`
Append-only server-side audit trail. Never update or delete rows. Required by CBK — retain for 7 years.

| Column | Type | Notes |
|---|---|---|
| `id` | BIGSERIAL PK | Sequential — preserves insertion order |
| `event` | TEXT | e.g. `MPESA_CALLBACK`, `MERCHANT_REGISTERED`, `RECONCILIATION_RUN` |
| `entity_type` | TEXT nullable | `transaction`, `merchant`, `consumer` |
| `entity_id` | TEXT nullable | UUID of the related entity |
| `detail` | JSONB nullable | Structured context — amounts, result codes, IP addresses |
| `ip_address` | TEXT nullable | Request origin IP |
| `created_at` | TIMESTAMPTZ | |

**Indexes:**
- `idx_audit_entity` on `(entity_type, entity_id)` — fast support queries (e.g. "all events for transaction X")
- `idx_audit_created` on `created_at DESC` — fast time-range queries

**Production note:** Ship this table to S3/GCS via a log forwarder (e.g. PgAudit + Fluent Bit). Local Postgres retention is not sufficient for a 7-year requirement.

## Migrations

The schema is managed by a single script at `src/db/migrate.ts`. It uses `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`, so running it multiple times is safe (idempotent).

```bash
npm run migrate        # apply schema
```

For production, graduate to a proper migration tool (node-pg-migrate or Flyway) that:
- Tracks which migrations have run (via a `schema_migrations` table)
- Supports rollbacks
- Can be applied incrementally during rolling deployments

## Useful Queries

```sql
-- Find all PENDING transactions older than 5 minutes (what the reconciliation job processes)
SELECT id, created_at, checkout_request_id
FROM transactions
WHERE status = 'PENDING'
  AND checkout_request_id IS NOT NULL
  AND created_at < NOW() - INTERVAL '5 minutes'
ORDER BY created_at ASC;

-- Merchant revenue summary (last 30 days)
SELECT
  m.name,
  COUNT(*) FILTER (WHERE t.status = 'CONFIRMED') AS confirmed_count,
  SUM(t.amount_cents) FILTER (WHERE t.status = 'CONFIRMED') / 100 AS confirmed_ksh
FROM transactions t
JOIN merchants m ON t.merchant_id = m.id
WHERE t.created_at > NOW() - INTERVAL '30 days'
GROUP BY m.id, m.name
ORDER BY confirmed_ksh DESC;

-- Consumer transaction history (masked phone)
SELECT
  t.id, t.status, t.amount_cents, t.mpesa_receipt, t.created_at,
  LEFT(c.phone, 5) || '****' || RIGHT(c.phone, 2) AS masked_phone
FROM transactions t
JOIN consumers c ON t.consumer_id = c.id
WHERE c.phone_hash = encode(sha256('254712345678'::bytea), 'hex')
ORDER BY t.created_at DESC
LIMIT 20;

-- Audit trail for a specific transaction
SELECT event, detail, ip_address, created_at
FROM server_audit_log
WHERE entity_type = 'transaction' AND entity_id = '<txn-uuid>'
ORDER BY created_at ASC;
```
