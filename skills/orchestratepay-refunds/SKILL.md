# OrchestratePay Refunds

Authoritative reference for the refunds subsystem. Covers the state machine, DB schema, API, admin approval flow, M-Pesa B2C integration, and failure recovery.

## Refund State Machine

```
PENDING ──► APPROVED ──► PROCESSING ──► COMPLETED
                │
                └──► FAILED
   │
   └──► REJECTED
```

| Transition | Trigger | Who |
|---|---|---|
| `PENDING` (initial) | Merchant POSTs `/api/v1/refunds` | Merchant |
| `PENDING → APPROVED` | Admin PATCHes with `action: APPROVE` | Admin |
| `APPROVED → PROCESSING` | B2C payout accepted by Daraja | System (admin PATCH handler) |
| `APPROVED → FAILED` | B2C payout API throws | System (admin PATCH handler) |
| `PENDING → REJECTED` | Admin PATCHes with `action: REJECT` | Admin |
| `PROCESSING → COMPLETED` | M-Pesa B2C callback confirms payout | Future: B2C callback route |

`REJECTED` and `FAILED` are terminal states that unblock a re-submission (they are excluded from the duplicate-refund guard).

## Database Tables

### `refunds`

Created by migration `002_new_features.sql`.

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | `uuidv4()` generated by the route |
| `transaction_id` | UUID FK → `transactions.id` | The original payment being refunded |
| `merchant_id` | UUID FK → `merchants.id` | Denormalised for fast merchant-scoped queries |
| `amount_cents` | INTEGER | Must be ≤ `transactions.amount_cents` |
| `reason` | VARCHAR(500) | Free-text merchant explanation |
| `status` | TEXT | `PENDING \| APPROVED \| PROCESSING \| COMPLETED \| REJECTED \| FAILED` |
| `initiated_by` | TEXT | Always `MERCHANT` for API-initiated refunds |
| `b2c_request_id` | TEXT | Daraja ConversationID returned by B2C call |
| `b2c_receipt` | TEXT | Daraja receipt on completion (set by future callback) |
| `approved_by` | TEXT | Admin sub from JWT (not currently stored — future enhancement) |
| `notes` | TEXT | Admin rejection reason or B2C failure detail |
| `created_at` | TIMESTAMPTZ | Set by DB default |
| `updated_at` | TIMESTAMPTZ | Updated on every status change |

### `transactions` (referenced, not modified)

The refund route reads `merchant_id`, `amount_cents`, and `status` to validate the request. The transaction record is never mutated — refund state is tracked separately.

## API Endpoints

### POST /api/v1/refunds

Auth: Merchant JWT (`requireAuth`).

Request body:
```json
{ "transactionId": "<uuid>", "amountCents": 5000, "reason": "Customer request" }
```

Validation rules (enforced before any DB query):
- `amountCents`: integer, 100–10,000,000 cents
- `reason`: string, max 500 characters
- `transactionId`: valid UUID

Business rules (checked sequentially, fail-fast):
1. Transaction must exist — 404 otherwise
2. Transaction must belong to the requesting merchant — 404 (same response as not-found to prevent merchant enumeration)
3. Transaction status must be `CONFIRMED` — 422 otherwise
4. `amountCents` must be ≤ `transactions.amount_cents` — 422 otherwise
5. No non-`REJECTED`/non-`FAILED` refund may already exist — 409 otherwise

Success: 201 `{ refundId, status: 'PENDING', amountCents, transactionId }`

### GET /api/v1/refunds

Auth: Merchant JWT (`requireAuth`).

Query params: `page` (default 1), `limit` (default 20, max 100).

Returns merchant's refunds joined with `transactions.mpesa_receipt`, newest first.

Response: `{ refunds: [...], total: <int>, page: <int>, limit: <int> }`

### GET /api/v1/refunds/:id

Auth: Merchant JWT (`requireAuth`).

The merchant_id filter is baked into the WHERE clause — a merchant can only ever see their own refunds. 404 for both "not found" and "wrong merchant" to prevent enumeration.

### PATCH /api/v1/admin/refunds/:id

Auth: Admin JWT (`requireRole('ADMIN')`).

Request body: `{ "action": "APPROVE" | "REJECT", "notes": "<optional string>" }`

## Admin Approval Flow

```
Admin sends PATCH /api/v1/admin/refunds/:id { action: "APPROVE" }
  │
  ├─ SELECT refund — 404 if missing
  │
  ├─ UPDATE refunds SET status = 'APPROVED'
  │
  ├─ call initiateB2cPayout({ refundId, merchantId, amountCents })
  │     │
  │     ├─ SUCCESS ──► UPDATE refunds SET status = 'PROCESSING', b2c_request_id = <id>
  │     │               return 200 with updated refund
  │     │
  │     └─ THROWS ──► UPDATE refunds SET status = 'FAILED', notes = <error message>
  │                    return 502 { error: 'B2C payout failed', refund: <failed row> }
  │
Admin sends PATCH /api/v1/admin/refunds/:id { action: "REJECT", notes: "..." }
  │
  ├─ SELECT refund — 404 if missing
  │
  └─ UPDATE refunds SET status = 'REJECTED', notes = <notes>
      return 200 with updated refund
```

## M-Pesa B2C Integration

The route calls `initiateB2cPayout` from `src/integrations/daraja.ts`. This function is a stub — it must be implemented before refunds can reach `PROCESSING` status in production.

Expected signature:
```typescript
initiateB2cPayout(params: {
  refundId:    string
  merchantId:  string
  amountCents: number
}): Promise<{ requestId: string }>
```

The `requestId` returned is stored as `b2c_request_id` and used to correlate the async Daraja B2C callback when it arrives. A future B2C callback route should:
1. Match `b2c_request_id` to a refund row
2. On success: set `status = 'COMPLETED'`, store `b2c_receipt`
3. On failure: set `status = 'FAILED'`, store error detail in `notes`

Daraja B2C environment notes:
- Sandbox shortcode: `600000` (Business-to-Customer)
- Requires separate OAuth credentials from the STK-Push credentials
- Result URL and Queue Timeout URL must be configured in Daraja portal

## Common Failure Modes and Fixes

### B2C throws immediately (status stays FAILED)

Cause: `initiateB2cPayout` not implemented, network error, or Daraja credential misconfiguration.

Fix: implement the function, verify `DARAJA_B2C_*` env vars are set, check Daraja sandbox/production portal for shortcode approval status.

### 409 Duplicate refund on resubmission

The duplicate guard excludes `REJECTED` and `FAILED` rows. If a refund is stuck in `FAILED` the admin must reject it first (setting status to `REJECTED`), which then allows the merchant to submit a new refund for the same transaction.

### 422 Transaction not CONFIRMED

The underlying transaction may still be `PENDING` (STK Push sent but M-Pesa callback not yet received) or `DECLINED`/`EXPIRED`. The reconciliation job (`src/jobs/reconciliation.ts`) expires stale `PENDING` transactions after 90 minutes — check that job is running before concluding a payment is lost.

### Over-refund rejected (422)

The route enforces `amountCents <= transaction.amount_cents` at the API layer. Partial refunds are supported; the same transaction can be refunded multiple times as long as earlier refunds reached `REJECTED` or `FAILED`. There is no cumulative-amount check across multiple refunds — if this matters for the business, add a `SUM(amount_cents)` guard in the duplicate-check query.

### Admin route not reachable

The admin PATCH is mounted at `PATCH /api/v1/admin/refunds/:id`. The refunds router is registered under both `/api/v1/refunds` and `/api/v1/admin` in `src/index.ts`. If the admin route returns 404, verify both `app.use` mounts are present.
